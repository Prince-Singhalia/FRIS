IMPORTANT PRODUCT ARCHITECTURE
There are two separate but connected automated pipelines:

A. RESEARCH DATA PIPELINE (the product workflow)
Faculty identity intake -> query planning -> scholarly source discovery -> author candidate resolution -> work retrieval -> raw/source landing -> schema validation -> cleaning/normalization -> identity confidence scoring -> DOI-first deduplication -> metadata reconciliation -> PostgreSQL persistence -> dashboard and review queue.

B. SOFTWARE CI/CD PIPELINE (software delivery)
Pull request/push -> lint/type checks -> unit/contract/integration tests -> security/supply-chain checks -> build versioned API, frontend and Prefect worker images -> deploy staging -> smoke tests -> controlled promotion -> rollback path.

Python implements connectors and transformations. Prefect orchestrates research data workflow tasks, schedules, retries, execution state and monitoring. GitHub Actions implements software CI/CD. Deployment MUST update the Prefect worker and flow code, not only the website/API.

FREE-FIRST STACK
- Backend: Python + FastAPI + Pydantic + SQLAlchemy.
- Database: PostgreSQL.
- Migrations: Alembic.
- Research workflow orchestration: self-hosted Prefect OSS.
- Frontend: React + TypeScript; charts with Recharts if needed.
- Containers/local deployment: Docker + Docker Compose.

- Backend tests: pytest; code quality: Ruff; add type checking where practical.
- Security/supply-chain checks: Gitleaks, Bandit, pip-audit and Trivy where available.

CURRENT REPOSITORY STATE FROM AUDIT
The current ZIP was a partial backend scaffold. It has FastAPI routes, SQLAlchemy model definitions, Pydantic schemas, faculty CRUD/import routes, login/JWT helpers, some production matching/normalization helpers, an abstract connector interface and a demo seed function. It does NOT yet provide a working end-to-end system.

Critical gaps identified:
- No concrete OpenAlex, Crossref, ORCID or Semantic Scholar adapters.
- No Prefect flow/tasks/deployment; discovery route only creates a pending DB job and does not submit a flow.
- Alembic versions directory is empty.
- Frontend source, package.json and Dockerfile are missing.
- `.github/workflows/` is empty; there is no software CI/CD.
- Some tests contain copied test-only implementations instead of importing production matching/dedup/normalization modules.
- CSV import unconditionally labels imported faculty as demo and does not persist previous affiliations.
- Faculty creation does not trigger discovery.
- Compose seed invocation is incorrect and migration errors are masked.
- Access and refresh token types are not properly distinguished by protected routes.
- Login query is not tenant-disambiguated.
- Connector status is configuration-derived rather than a real status.
- DOI normalization/validation is too permissive.
- Confidence scoring helper is not fully wired to the evidence model.
- Git repository has no useful commit history yet.

The prior audit ran `python -m compileall -q backend/app backend/tests` successfully and `python -m pytest -q` with 56 passed, 2 failed (58 total). The two failing tests incorrectly use `0000-0002-1825-009X` as a valid ORCID. Replace that fixture with the checksum-valid `0000-0002-1694-233X`; do not weaken the production checksum validator. Ruff and Docker were not available in the audit environment, so their status was NOT RUN, not passed.
